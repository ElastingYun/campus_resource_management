## 2. 后续实现的行为验收矩阵

| 对应需求 | 正常场景与可观察结果 | 失败和边界场景 |
| --- | --- | --- |
| E-REQ-01 上报 | 合成用户对可用教室上报一次故障，获得稳定工单 ID；本人按授权范围读到记录 | 教室不存在/停用、无权教室、空或超长描述、同键同内容重试只生成一单、同键不同内容拒绝 |
| E-REQ-02 派单/维修 | 有权人员按合法顺序派单、开工、完工；历史记录操作者、时间与前后状态 | 未授权、跨教室、重复操作、错误顺序、并发双人派单及旧版本覆盖被拒绝 |
| E-REQ-03 升级 | 配置的阈值达到时只产生一次升级意图，相关人员可查到状态 | 阈值前后一分钟、恰好阈值、重复扫描、任务停机后恢复、通知不可用与重试不重复告警 |
| E-REQ-04 验收 | 完工进入待验收仍保持下架；合格验收触发解除；评价按批准规则记录 | 无权限/自验收限制、验收失败返修、重复验收、完成即误解除、评价越权 |
| E-REQ-05 下架 | 独立运行的 M3 经 HTTP 写入 M1 的 `m3_repair` 整室来源；A 的搜索与提交均阻止新预约 | 现有预约、并发预约与下架、房间 ID 不匹配、同 ID 参数冲突、跨服务凭据无权 |
| E-REQ-06 解除 | 验收通过只解除本工单来源；M1 仍正确保留另一维修或审批限制 | 完工未验收、两个工单只验收一个、M2 同时占用、重复解除、旧下架请求晚到 |
| E-REQ-07 权限隐私 | 本人和授权维修/验收人员只见各自范围的数据；公共审计留最小必要字段 | 匿名、伪造角色/院系/教室头、越权列表/详情、敏感描述或凭据写入日志 |
| E-REQ-08 恢复 | M1 已写成功但响应丢失，M3 按原来源查询后收敛为确认；重启后继续处理 | M1 不可达、超时、坏回执、查询无记录、来源内容不匹配、重试耗尽进入人工核查；不误报成功 |

测试应通过公开 API、数据库中实际状态及用户可见的查询结果断言行为。需要真实 PostgreSQL 验证事务、唯一约束、并发与迁移；需要独立运行的 M3/M1 实例验证最终网络写回。Mock 可隔离外部故障，但不能替代真实网络验收。

## 3. 一条正常链路与一条未知结果链路

**正常链路（待接口批准后执行）**：用合成用户登录 → 创建工单 → 派单 → 开工 → 在 M3 查询中看到下架已确认 → 在 A 的可用性/预约接口观察整室不可预约 → 完工后仍不可预约 → 验收通过 → 确认该工单来源被解除 → 如另有维修/M2 占用，整室仍不可预约。每一步记录工单 ID、来源 ID、实际 HTTP 状态及测试环境，不记录凭据。

**未知结果链路（待接口批准后执行）**：启动独立 M1/M3 → 让 M1 成功写入限制但丢弃响应 → M3 将结果标为待核实 → 用固定工单 ID 查询 M1 并恢复确认 → 重启 M3 后不新增第二条限制。再模拟 M1 不可达，确认业务查询没有把限制状态显示为成功，并保留待恢复操作。
