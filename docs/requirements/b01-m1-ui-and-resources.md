## 1. B 的范围与边界

| 范围 | B 的责任 | 依赖与边界 |
| --- | --- | --- |
| M1 前端 | 搜索、预约、签到、历史、资源管理、运营查看六类页面 | 调用 A 的预约接口及 C 的身份权限接口 |
| 教室与座位主数据 | 字段草案、管理页面、后续资源接口及对应测试和迁移 | 共享模型、权限、迁移方式须先评审 |
| 页面公共状态 | 加载、空结果、校验错误、权限拒绝、网络失败和成功反馈 | 展示服务端真实结果，不伪造成功 |
| 本人交付证据 | 需求追踪、测试、迁移说明、AI 参与与人工验收记录 | F 组织集成，D 接入工程与流水线 |

不包含：A 的冲突检查、签到判定、定时任务、违约处理和动态可用性计算；C 的认证/RBAC/审计实现；E 的通知发送；D 的统一脚手架与部署；F 的全组集成组织。

## 2. 已知硬规则与页面表现

下列要求来自任务书及仓库课程约束；其中“每天更新教室码”依据任务书第 6 页，精确时间边界、错误码和显示方式仍需接口评审。

| 编号 | 已知规则 | B 的可观察交付 |
| --- | --- | --- |
| B-HARD-01 | 按整点小时预约；单次默认最多 4 小时，可配置 | 时间选择器按已确认粒度输入，展示服务端提供的当前时长上限；服务端仍复核 |
| B-HARD-02 | 签到码/二维码与教室关联，每天更新 | 展示与对应教室关联的码及有效信息；生成和有效性判断由 A 负责 |
| B-HARD-03 | 开始前 15 分钟提醒，开始后 10 分钟未签到再次提醒 | 需要展示提醒时读取真实结果；通知触发由 A 与 E 协作，页面不充当定时器 |
| B-HARD-04 | 开始后 15 分钟未签到，自动取消、释放并记违约 | 刷新或重新进入后展示后端的取消及违约结果，不由前端自行执行处罚 |
| B-HARD-05 | 支持院系准入限制、插座筛选、历史及运营查询 | 使用已授权数据展示资源与记录；院系限制必须由后端执行 |
| B-HARD-06 | M2 批准时段占用全室；M3 维修中下架，验收通过后按规则恢复 | 查询和提交预约均遵守 A 的动态可用性结果，展示获准公开的不可用原因 |

开始前后各阈值的等号归属、时区和允许签到区间由 A 提案确认；本文不据此新增规则。
多个占用/维修原因叠加时，取消单一原因不代表资源恢复，B 不自行推断“可预约”。

## 3. 页面需求与验收标准

以下为六类页面，编号用于需求→Issue→PR→测试追踪；具体验收用例见[验收计划](../testing/b01-acceptance-plan.md)。

| 编号 | 页面及目标 | 拟验收标准 |
| --- | --- | --- |
| B-UI-01 | 座位搜索：按日期、时段、教室和插座条件查找 | 输入合法条件后发送约定参数；呈现 A 返回的座位及可用性；无结果、加载和失败可区分；不会将未知状态显示为可预约 |
| B-UI-02 | 座位预约：选定座位及时间后提交 | 提交前展示座位与时段；成功后显示后端预约标识及状态；冲突、无权限、资源变化时明确提示；请求未完成时避免重复点击 |
| B-UI-03 | 签到：提交对应预约的教室码 | 展示本人预约信息；提交编码给 A；成功、错误码、无权限及失效结果分别可见；失败后不显示已签到 |
| B-UI-04 | 我的预约与历史：查看记录、违约及再次预约 | 仅展示授权范围内的记录和真实状态；历史再次预约预填资源选择，并要求选择新时段、重新查可用性与提交，不沿用过去的成功结果 |
| B-UI-05 | 资源管理：维护教室、座位及配置 | 获授权管理员能够新增、修改和查询资源；非法字段有提示；失败后保留可恢复的表单输入；停用/注销操作在冲突政策确认前不进入实现 |
| B-UI-06 | 运营查看：查看资源预约情况 | 根据经确认的日期/教室条件读取 A 的运营数据；空态、权限拒绝和失败可区分；只展示已批准字段，不自行定义统计口径或公开个人资料 |

B-UI-03 的签到码展示子页：仅允许经 C 确认的角色读取对应教室当日编码；码由 A 生成和轮换，B 展示并处理过期或获取失败。
二维码的载荷、刷新方式、展示终端和是否包含可公开内容，待 A/C 确认后补充验收。
若某项后端能力尚未提供，页面不得用固定假数据作为集成完成证据；开发演示的合成数据需明确标记。
预约取消入口、运营指标、分页/排序/自动刷新方式均是待评审项，不作为本文已确认功能承诺。

## 4. 资源主数据需求与验收标准

字段与接口详见[资源 API 草案](../architecture/b01-resource-api-draft.md)，本文不批准数据库 schema。

| 编号 | 需求 | 拟验收标准 |
| --- | --- | --- |
| B-RES-01 | 教室基础信息 | 可录入并查询名称、位置、院系归属等候选字段；必填/长度/唯一性约束按批准契约校验；无效请求不写入数据 |
| B-RES-02 | 座位与教室关联 | 每个座位关联有效教室，并维护座位标识与插座属性；不存在的教室及重复标识按确认规则被拒绝 |
| B-RES-03 | 开放时间 | 可维护和查询约定格式的开放时间；无效时间段被拒绝；A 能通过公开接口取得配置用于预约判断 |
| B-RES-04 | 院系开放范围 | 可表达团队批准的准入范围；服务端按 C 的规则验证查询与写入权限；其他院系用户不得绕过前端预约受限资源，资源元数据可见范围待 C 确认 |
| B-RES-05 | 静态启用状态 | 资源可保存静态启用配置；它与 A 计算的时段可预约性使用不同概念和字段；B 不通过启用操作覆盖有效占用或维修状态 |
| B-RES-06 | 资源维护权限与失败反馈 | 匿名、普通学生及越权管理员的写入按 C 的规则拒绝；合法操作获得真实结果；必要审计通过 C 提供的约定记录 |
| B-RES-07 | 数据迁移与初始化 | 实现时提交版本化迁移和合成种子数据；从空库可重放；重复初始化不产生重复资源；具体工具遵循 D 的工程决策 |

`enabled` 仅表示管理员维护的静态启用配置；`availability` 表示 A 根据具体时段、开放时间、权限及 M1/M2/M3 原因计算的动态结果。
即使 `enabled=true`，座位也可能不可预约；B 的管理接口不提供直接写动态 `availability` 的能力。
字段名只是候选，不代表共享模型已获批准；主数据更新对现有预约的影响必须先决策。
本轮不定义硬删除、级联删除、停用自动取消预约或批量注销策略。
