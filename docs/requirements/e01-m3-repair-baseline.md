## 1. 本轮交付与所有权

本轮只建立可供团队逐项决策的需求、接口与验收草案。后续 E 负责 `backend/app/modules/m3_repair/` 中的工单后端、对应测试及迁移；公共通知能力位于 `backend/app/common/notifications/`，另与 C 的 [#25](https://github.com/ElastingYun/campus_resource_management/issues/25) 对齐。F 负责报修页面和跨模块集成组织。A 负责 M1 座位限制及动态可用性，B 负责教室/座位主数据，C 负责可信身份、权限和审计，D 负责统一工程入口、迁移和运行接线。

| 编号 | 业务能力或边界 | 验收方向 | 决策状态 |
| --- | --- | --- | --- |
| E-REQ-01 | 有权限的人上报教室故障，工单关联稳定教室标识、描述和提交者 | 合法请求留下可查询记录；无效教室、越权和重复提交有确定结果 | 必须具备；谁能报修、字段和公开范围待确认 |
| E-REQ-02 | 有权限的人派单、更新维修进度并记录操作者及时间 | 只允许合法状态转换；无权限和过期版本不改动工单 | 必须具备；派单范围及转派规则待确认 |
| E-REQ-03 | 满足升级条件时提醒相关责任人，并留下可追踪记录 | 多次扫描不重复升级；时间边界可测 | 必须具备；时限、收件人及告警渠道待确认 |
| E-REQ-04 | 完工后由获授权人员验收；可记录评价 | 完工本身不解除维修限制；验收通过才允许解除该工单来源 | 必须具备；验收人、失败返修、评价规则待确认 |
| E-REQ-05 | “维修中”工单使所属整间自习室停止接受新的座位预约 | 经 A 的公开网络接口写入 `m3_repair` 来源，M1 可追溯 | 已确认跨模块效果；写入失败时的业务状态待确认 |
| E-REQ-06 | 验收通过后解除**本工单**引起的限制 | 其他维修、审批或预约仍生效；不能直接改 B 的静态 `enabled` | 已确认边界；恢复失败时的展示和处理待确认 |
| E-REQ-07 | 查询和写入按可信身份、角色、教室范围限制 | 后端拒绝越权；前端隐藏按钮不作为授权依据 | 必须具备；权限矩阵由 E/C/F 决定 |
| E-REQ-08 | 重复请求、响应丢失和服务重启不造成重复工单或错误释放 | 能按原请求标识查询结果并恢复；未知结果不能伪装成功 | 必须具备；保留时限与重试预算待确认 |

## 2. 候选状态机

以下状态名与转换是**讨论提案**，只有“维修中下架、验收通过后按规则恢复”是仓库已确认的跨模块要求。状态反映工单业务事实；M1 限制的执行结果应单独记录，不能把工单 `REPAIRING` 当成远端一定下架。

| 当前状态 | 候选操作与下一状态 | 候选操作者 | 需要确认的条件与副作用 |
| --- | --- | --- | --- |
| 无 | 上报 → `REPORTED` | 报修人 | 身份、房间资格、重复请求及内容可见性 |
| `REPORTED` | 派单 → `ASSIGNED` | 派单员 | 维修人员资格、派单范围、是否允许拒单或撤回 |
| `ASSIGNED` | 开工 → `REPAIRING` | 维修人员 | M1 整室下架何时必须确认；未确认时能否进入此状态 |
| `REPAIRING` | 完工 → `AWAITING_ACCEPTANCE` | 维修人员 | 完工证据、隐私字段；此时仍保留下架 |
| `AWAITING_ACCEPTANCE` | 通过 → `ACCEPTED` | 验收人 | 验收权限、与维修人是否必须分离；发起仅针对本工单的 M1 解除 |
| `AWAITING_ACCEPTANCE` | 不通过 → `REPAIRING` 或独立返修状态 | 验收人 | 是否返修、是否保留原派单及限制，尚未决定 |

`ACCEPTED` 为候选业务终态；但它**不等于** M1 已确认解除。应提供独立的限制执行状态供查询与恢复。取消、撤回、转派、重开、关闭和评价写入的时间窗口均未获批准，本轮不把它们加入确定转换。升级提醒可与工单状态并存，不擅自新增业务终态。

## 3. 跨模块不变量

1. M3 只持有工单与本模块的执行记录。B 的主数据、A 的座位限制、C 的身份/审计各有所有者。M3 通过公开接口核对教室和写回限制，不直接改其他模块的表。
2. 下架范围是**整间自习室**，来源至少要能用工单 ID 唯一识别。M1 只解除相同来源，不因一张工单验收而把教室直接置为可预约。
3. 维修状态、远端限制状态、通知投递状态是不同事实。跨服务写入超时可能已经生效；在查询或同标识重试确认前，向用户显示“待核实”。
4. 既有预约受维修影响时，是否取消、如何通知及是否记违约属于 A/E/C/F 共同决策。M1 候选实现会返回受影响预约 ID，并不会替 M3 自动取消。
5. 工单描述、图片、联系方式、评价及验收意见可能含私人信息。只保存业务必需内容；字段白名单、可见范围、脱敏、保留期限和附件策略先由 C/E/F 确认。示例只用合成数据。
