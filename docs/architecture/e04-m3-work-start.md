# E-04：维修开工规则与限制确认边界

关联 [Issue #73](https://github.com/ElastingYun/campus_resource_management/issues/73)。E 负责人决定以下 **M3 内部规则**；A 的 M1 网络契约、C 的可信身份和审计适配、D 的主应用接线仍须相应负责人评审。本增量叠加在 E-03 派单分支上，不表示完整维修流程已上线。

## E 的开工决定

1. 只有工单当前指派的维修人，并且其可信主体具有 `can_start_repair` 能力，才能开工。浏览器不能自行声明身份或能力。不是被指派人时返回 403。
2. `ASSIGNED → REPAIRING` 前，必须经可信 `RestrictionConfirmation.require_active(ticket_id, room_id)` 确认 M1 对**同一工单来源、同一教室**已有生效的整室维修限制。端口未配置、远端不可达、来源或教室不匹配、状态未知时不得开工。B 的静态 `enabled` 或 M3 本地状态不是下架证明。
3. `POST /api/v1/m3/tickets/{ticket_id}/work-starts` 使用可信会话、UUID `Operation-Id` 请求头和 `{"expected_version":1}`。首次成功返回 201、`REPAIRING`、版本 2；相同操作标识、操作者与版本重试返回 200 和原结果；跨动作复用操作标识或旧版本返回 409。版本条件更新防止确认期间工单被其他人改变。
4. 工单状态、M3 操作历史和成功审计在同一数据库事务提交；审计失败则全部回滚。审计只写可信主体、工单/教室 ID、操作标识、前后状态和时间，不写故障描述。M1 确认是外部事实，不与 M3 数据库事务伪装成一个分布式事务。

现有 E-03 操作历史表足以保存本次 `start` 事件，无新迁移。`AssignmentAudit` 与 `WorkStartAudit` 是不同动作的端口；具体 C 审计动作名由 C/E 对齐。当前生产默认端口返回 503，只有合成测试适配器可走通此流程。

## 还未完成的接入

E 还需实现“向 M1 发起整室下架并持久恢复未知结果”的独立任务。A 的公开限制接口已有候选契约，但 M3 服务身份、请求参数固定化、响应核对及真实网络联调尚未验收。此任务只负责**确认后开工**，不自动调用 M1 写入，也不把 503 当成正常开工。D/C/E 还需处理迁移汇合、主应用挂载和可信能力注入。维修完工、验收和解除限制仍是后续独立任务。
