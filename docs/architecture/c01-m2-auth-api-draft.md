# C-01：M2、身份权限与审计接口草案

## 1. 所有权与运行边界

| 领域 | 提供者 | 可公开接入的能力 | 禁止的捷径 |
| --- | --- | --- | --- |
| 身份与权限 | C | 可信身份上下文、权限/范围判定、会话生命周期 | 信任浏览器传入的角色、院系或任意用户标识 |
| M2 | C | 申请、审批、历史、超时处理与集成结果 | 直接修改 M1 座位状态或 B 的资源表 |
| 资源 | B | 稳定教室/院系引用与批准公开的配置 | 以静态 enabled 推断动态可预约性 |
| 动态占用 | A | 原子占用、来源释放、执行结果查询 | 用 M2 的查询预检查替代 M1 最终并发校验 |
| 通知 | E | 发送及发送结果的公开契约 | C 自建另一套通知发送逻辑 |
| 审计 | C | 有授权的事件接收与查询 | 允许普通调用方冒充操作者、覆盖已有审计 |

代码可以处于同一仓库；进程、数据库、任务运行方式与身份验证位置由 D 组织 ADR。
最终 M2→M1 联调使用独立运行实例之间的网络契约，不把公共模块导入或进程内函数调用当作该链路的证据。
公共认证/审计的本地入口与跨实例接入方式分别评审，不默认增加独立认证服务或跨模块共享数据表。

## 2. 公共身份与授权候选契约

### 2.1 身份上下文

`Principal` 是可信服务端上下文候选，至少讨论以下内容：

| 字段 | 候选含义 | 约束 |
| --- | --- | --- |
| subject_id | 当前用户稳定标识 | 从有效认证结果取得，不能用请求体指定申请人 |
| department_id | 经确认的院系关联 | 标识与来源同 B 对齐，不信任客户端声明 |
| roles / permissions | 角色展示与操作许可 | 枚举及授予方式待定；前端展示不替代服务端校验 |
| data_scopes | 管理/查询的资源或院系范围 | 空、缺失及全局范围的含义必须明确，不能默认全权限 |
| session_ref / auth_version | 会话关联及失效判定信息 | 对外只返回获准公开字段，不暴露会话秘密 |

授权入口至少区分“是否登录”“是否可执行动作”“是否可操作该对象”；拒绝优先，不能靠猜不到标识防止越权。
当前身份查询仅供 UI 展示与交互，所有业务请求仍重新检查当前权限。
会话撤销、用户停用与角色调整的传播时限必须有精确验收界限，不能把令牌存在等同权限永久有效。

### 2.2 认证 API 候选

以下相对路径以 `/api/v1/auth` 为讨论前缀。登录凭据格式和会话交付机制待 C-OPEN-01 决策。

| 方法与路径 | 意图 | 请求/响应边界 |
| --- | --- | --- |
| `POST /sessions` | 登录并建立会话 | 输入批准的凭据；失败不区分可用于枚举账号的内部细节；成功返回获准身份信息并交付会话 |
| `DELETE /sessions/current` | 退出当前会话 | 按可信会话定位并撤销；重复退出语义及 CSRF 约定待定；退出后旧会话不可再授权 |
| `GET /me` | 获取当前身份 | 返回获准公开的 Principal 投影，不返回密码散列、会话秘密或任意用户的授权详情 |

首轮推荐合成账号与服务端可撤销会话，统一身份提供者作为后续适配；JWT/续期方案仅作为备选，未经决策不同时实现两套。
Cookie 模式需确定 HttpOnly、HTTPS 下 Secure、SameSite、CSRF、CORS 和代理；Bearer 模式需确定浏览器存储、撤销和续期。
会话过期、失败限流、密码散列及账号引导使用成熟依赖，具体包、版本与新增理由在实现计划中列明。
不提交真实账号、初始密码、生产密钥或 `.env`；演示账号的初始化方式与安全示例由 D/C 确认。

### 2.3 权限矩阵候选

下表是能力分类，不是已授予的角色。权限命名和真实角色映射由 C/B/D 与受影响成员批准。

| 能力 | 拟允许的行为 | 额外对象条件 |
| --- | --- | --- |
| 申请提交 | 创建本人申请 | 账号有效，满足申请资格及资源准入政策 |
| 本人申请查询 | 列表、详情、允许公开的历史 | 对象属于本人；不能通过筛选参数切换用户 |
| 节点审批 | 查看待办并通过/驳回 | 当前节点、对应资源范围、自审/替补政策均满足 |
| 运营查询 | 查询批准范围的申请 | 院系/资源范围和字段白名单，不能默认读取全校个人信息 |
| 资源管理 | 使用 B 的管理接口 | 管理范围由 B/C 对齐，不能推导出审批或审计查看权限 |
| 签到码展示 | 读取 A 的相应教室码 | 展示终端/角色和资源范围需 A/B/C 单独批准 |
| 审计查询 | 按批准条件读取审计 | 独立权限与数据范围，不随普通管理员角色自动获得 |
| 权限管理 | 授予/撤回角色 | 首轮是否开放管理 API、谁能授权及防提权规则待定 |

业务调用身份与服务调用身份分别验证。普通浏览器不能以 `source=M2` 或自填 actor 获得内部占用/审计权限。
服务如何证明调用方、如何传播用户上下文及区分系统超时操作者，由 ADR 和安全契约明确。

## 3. 审计候选契约

### 3.1 事件与访问

建议事件包含 `event_id`、操作者类别/标识、动作、目标类别/标识、发生时间、结果、必要的状态变化、`request_id` / 业务操作关联标识和事件结构版本。
系统超时任务明确记录为系统动作，保留相关申请与操作标识，不冒充原申请人。
服务接收端验证发送方身份、事件类型权限和上下文来源；不因调用方能联网就信任任意 actor 或结果。

- 本地业务成功与本地审计记录同一事务提交，避免只有状态没有审计。
- 跨实例调用方先持久化待发送事件；接收方按事件标识去重，同标识不同内容作为冲突处理。
- 失败/拒绝事件采用独立于被回滚业务事务的可靠记录路径，并受输入白名单和限流约束。
- 审计写入失败时是否阻断对应业务、重试与告警/人工处理方式须由 C-OPEN-08 决策；不静默丢弃或假报成功。
- 无普通业务编辑/删除入口；保留期限、脱敏和归档由团队决定，不承诺数据库管理员无法篡改的审计能力。

网络接入与查询路径建议以 `/api/v1/audit` 为前缀：

| 方法与路径 | 意图 | 授权边界 |
| --- | --- | --- |
| `POST /events` | 可信服务提交审计事件（如 ADR 采用网络接入） | 仅授权服务；服务身份不等于任意用户身份；去重、持久化成功后才确认接收 |
| `GET /events` | 查询批准可见的审计 | 单独授权并过滤范围；筛选、分页与字段白名单待确认 |

无批准前不开放公共事件写入或审计管理页面。采用本地接入时同样维护版本化事件结构，不绕过发送模块的数据所有权。

### 3.2 数据最小化

禁止记录密码、会话/刷新令牌、Authorization/Cookie 内容、签到码原文、完整请求体或真实学生私人资料。
申请用途、驳回意见只在批准的业务查询中按权限公开；审计按必要字段或脱敏摘要记录，长度、换行及日志注入输入需要验证。
请求关联标识不作为认证凭据；外部传入标识需校验格式，不允许通过日志注入制造伪审计。

## 4. 错误、持久化与评审约束

候选错误语义：无有效身份 `401`，缺少许可 `403`，不存在或按批准策略隐藏 `404`，状态/版本/幂等内容冲突 `409`，输入不合法 `422`，登录请求限流 `429`。
状态码与机器错误码、可公开信息及重试建议由团队统一；不在错误里返回内部栈、SQL、秘密或他人资料。
对超时的写操作，响应或查询必须能表达“结果未知/处理中”；不能因 HTTP 失败就认定业务没有执行。

认证候选持久化对象是用户、角色/权限关联、作用范围与会话；审计对象是事件及必要的可靠投递记录。
这不是已批准表清单；标识类型、索引、保留/失效、迁移和数据所有权另经评审，不跨模块建立可直接修改他人表的捷径。
与统一工程绑定的事务、依赖注入、连接、密钥配置和 HTTP 客户端遵循 D 的标准。
