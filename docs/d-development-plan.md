## GitHub 与 AI 协作方式

我按“需求 → Issue → AI 实施计划 → 人工确认 → 独立分支 → 实现与验证 → PR → 非作者 Review → 修正 → 合并”推进。一个 Issue 对应一个可审查的主要目标；分支示例为 `docs/d01-development-and-initialization`、`feat/d02-engineering-bootstrap`、`ci/d03-quality-gates`。

Issue 写清负责人、范围、依赖和可观察的验收标准。PR 关联真实 Issue，说明行为变化、实际测试命令和结果、AI 参与范围、人工待验收项、迁移与跨模块影响。依赖尚未合并时，我会明确 PR 的基线和合并顺序，不直接推送 main。

AI 帮我分析、实现、测试、定位失败和整理文档；我负责确认关键规则、检查差异并验收。另一位真实成员完成同行 Review，AI 辅助审查不算非作者人工批准。提交数量、自动化生成的文字或未执行的测试不能替代贡献和质量证据。

建议 F 组织团队看板：待梳理、可开发、开发中、待评审、完成，另标阻塞原因。每位成员同时推进一个主要任务。仓库管理员配置 main 的 PR 审核与必要检查，不能把“CI 已存在”写成“分支保护已启用”。
