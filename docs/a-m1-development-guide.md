## 1. 我的职责与交付范围

我作为 A 负责 M1 后端，目标是让学生能够查询座位、按规则预约、完成签到、查看自己的历史，并确保并发请求、整教室审批和维修不会导致错误占用或错误释放座位。

我的交付物包括业务代码、相应测试、版本化数据库迁移、M1 需求与接口说明、真实验证记录，以及可以追踪到任务的 Commit 和 PR。前端页面由 B 负责，我负责提供可供 B 调用和验证的接口。

## 3. 已确认规则与待决问题

### 3.1 已确认，必须实现

| 规则 | 验收重点 |
| --- | --- |
| 按整点小时预约，单次默认最多 4 小时，可配置 | 非整点、零/负时长、超过上限应按契约拒绝；上限配置应生效 |
| 同一座位重叠时段不可重复预约 | 多个请求同时提交也不能产生双重有效占用 |

| 开始后 10 分钟仍未签到，再次提醒 | 已签到者不能收到错误的未签到提醒 |
| 开始后 15 分钟仍未签到，取消预约、释放座位、记录违约 | 不能重复记录违约，不能误释放其他来源的限制 |
| 支持院系限制、插座属性、预约历史与运营能力 | 筛选和授权在后端执行，个人记录不可越权读取 |

| M3 维修中使整间自习室下架，验收通过后按规则恢复 | “维修完成”不能直接替代“验收通过”；多工单不能相互误释放 |
| 占用、下架、释放可追溯 | 保留来源类别、业务 ID、发生时间和状态转换证据 |

### 5.2 数据概念，先确认归属再建表

- **预约记录**：关联用户和座位、起止时间、业务状态、签到信息及必要时间戳；具体字段和状态枚举待契约确认。
- **资源限制来源**：区分个人预约、M2 审批占用和 M3 维修下架，记录来源业务 ID、作用范围、有效期及释放依据；具体表结构待评审。
- **违约记录**：关联预约和触发依据，支持按批准规则追溯与纠正；不擅自引入处罚政策。
- **处理幂等信息**：用于重复预约、状态写回和任务重试；保存位置、保留期及响应行为需在契约中约定。

教室和座位主数据由 B 负责，身份和公共审计由 C 负责，通知发送记录由 E 负责。我通过批准的公开契约使用这些能力，不复制其他模块的业务逻辑或直接写入其表。M1 数据库迁移由我使用批准工具编写，并验证从空库顺序重放。

### 5.3 并发和状态正确性

可用性查询只反映查询时刻的结果，最终预约写入仍须在事务中重新校验并获得并发保护。“先查询为空再插入”本身不足以防止同时抢座。

我会与 D 和相关 owner 评审数据库约束、锁和事务策略，覆盖个人预约之间的冲突，以及 M2/M3 写回与预约同时发生的竞争。具体 PostgreSQL 实现及迁移方案将单独形成可审查变更。

我会在契约中明确重复请求的处理方式：相同幂等标识和相同参数如何返回；相同标识但参数不同如何拒绝；不同用户之间如何隔离。签到、超时取消、违约和通知重试均需处理重复执行。

释放操作必须指向明确来源。撤销一个审批或验收一个工单后，重新考虑其他仍有效的审批、预约和维修限制，不能简单把座位写成“可用”。

## 6. 接口设计与协作方法

我先按下表梳理接口能力，再与 B/C/E 确认具体 URL、字段和版本。目前这些接口尚未实现。

| 接口能力 | 调用方 | 重点约定 |
| --- | --- | --- |
| 查询座位及某时段可用性 | B 的 M1 页面 | 筛选、分页、资格限制、时间表示、空结果 |
| 创建预约 | 已认证学生 | 用户身份来自认证上下文；时段、座位、冲突与幂等 |
| 查询本人预约/历史 | 已认证学生 | 后端限制数据范围；分页与状态筛选 |
| 主动取消 | 预约本人或经授权运营人员 | 已批准的取消规则；状态转换与来源释放 |
| 签到 | 预约本人 | 动态编码、预约归属、教室和时间窗口 |
| 运营查询及操作 | 经授权运营人员 | 明确 RBAC 权限、数据范围和审计 |
| 添加/撤销审批占用 | 经鉴权的 M2 服务 | 审批 ID、教室、时段、重复和乱序处理 |
| 添加/解除维修限制 | 经鉴权的 M3 服务 | 工单 ID、教室、维修与验收依据、重复和乱序处理 |

我编写的每个契约都会明确版本、输入约束、请求/响应示例、认证与授权、错误码、事务结果、重复调用行为、超时重试语义，以及通知/审计副作用。权限判断以可信身份和后端授权为依据，不能仅采信调用方传来的用户 ID、角色或来源字段。

跨模块演示必须在独立运行的服务之间真实发起网络请求。是否拆成多个 FastAPI 运行实例以及如何部署，由 ADR 决定。开发中的 mock 可用于隔离测试，但不能充当最终网络集成证据。

## 7. 测试与验收清单

我通过接口响应、数据库有效状态、限制来源、事件或发送记录来验证业务行为。测试中的 mock 只用于必要的外部依赖隔离，不替代被测业务逻辑。

| 功能 | 正常路径 | 失败和边界 |
| --- | --- | --- |
| 搜索 | 返回符合时段、院系和插座条件的座位 | 无结果、非法筛选、无资格、维修/审批限制、分页边界 |
| 时间校验 | 合法整点小时；默认上限 4 小时 | 非整点、起止相同、结束早于开始、超过配置上限、跨日与时区按批准规则 |
| 预约冲突 | 不冲突预约成功 | 同座位完全/部分重叠、包含关系、相邻边界、取消后的可用性 |
| 并发预约 | 同时抢同一座位，最多一个有效占用 | 独立请求与事务真实并发；失败方有明确冲突响应，数据库无残留占用 |
| 请求幂等 | 重试不生成第二条预约或副作用 | 相同标识不同参数、不同用户标识隔离、处理中重试 |
| 权限 | 本人查阅和操作获准记录 | 未登录、读取/取消/签到他人预约、学生调用运营或跨模块接口 |
| 签到 | 正确预约、教室和有效编码成功 | 错误/过期编码、重复签到、窗口前后、恰好在截止点与取消任务竞争 |
| 提醒 | 前 15 分钟；后 10 分钟且未签到 | 已签到/已取消、重复扫描、通知失败、延迟任务和时间边界 |
| 自动取消 | 后 15 分钟仍未签到，取消并记录一次违约 | 重复执行、并发签到、部分失败、系统故障按批准规则处理 |
| M2 写回 | 审批时段内整室受限，撤销释放对应来源 | 既有预约冲突、重复/乱序事件、网络超时与补偿 |
| M3 写回 | 维修下架，验收通过后解除对应限制 | 仅维修完成、两个工单只验收一个、仍有审批或个人预约 |
| 跨来源竞争 | 预约、审批、维修限制一致生效 | 同时写入、回滚失败、旧事件重试，不出现错误恢复 |
| 迁移 | 空库升级成功，数据约束符合契约 | 重复种子执行、已有数据升级、失败后的批准恢复路径 |

时间任务应使用可控制的测试时钟或团队批准的等价机制，避免测试依赖真实等待 15 分钟。临界点的预期结果必须来自已批准规则。

并发、数据库约束和迁移测试应使用真实 PostgreSQL 验证；跨模块最终验收应使用真实网络服务，不能仅以 mock 测试替代。

按照项目要求，我会在隔离测试环境选一个关键保护做“临时破坏实现 → 对应测试失败 → 恢复实现 → 测试通过”，保存真实命令和结果。交付前恢复正确实现，保留有效断言和测试。

我会在每次验证中记录实际执行命令、环境、提交或工作树状态、通过/失败数量、关键输出以及未运行项及原因。当前应用测试、构建、迁移和 CI 均为 **NOT RUN：工程尚未初始化**。

## 8. 我的提交节奏与过程记录

### 8.1 区分 commit 和 push

`git commit` 创建版本记录，`git push` 把已有提交同步到 GitHub。反复 push 同一个提交不会增加提交记录；一次 push 也可以包含多个有意义的提交。

我的开发节奏是：**开发期间约每 30 分钟检查一次进度，将已完成、已验证并经我验收的小改动提交并推送到任务分支。** 尚未达到提交条件时，我会记录阻塞并继续完成该任务。检查节奏服务于真实进度记录，不要求每次检查都产生新提交。

### 8.2 每个检查点的步骤

1. 检查分支和工作区，确认改动只涉及当前 Issue 与授权文件，没有混入其他成员的未提交工作。
2. 查看 diff，运行与变更相关且当前实际存在的检查；未运行或失败必须如实记录。
3. 由我按 AGENTS.md 检查 diff、运行可执行测试并验收；如使用 AI 辅助，另行记录其参与范围。
4. 只暂存审阅过的明确文件，写明做了什么以及原因，关联实际 Issue。
5. 推送当前任务分支；记录提交 hash 和 push 结果。网络失败保留本地提交，排查后重试，不重建提交来凑次数。
6. 达到任务验收标准后建立 PR，交非作者 Review；功能开发不直接推送 main。

我使用以下只读命令检查当前改动：

```bash
git status --short --branch
git diff --stat
git diff
git diff --check
git diff --cached
git log -5 --oneline
```

`git diff` 不展示未跟踪新文件的完整内容；还需根据 `git status` 单独阅读新增文件，暂存后再审查 `git diff --cached`。格式检查不能替代业务测试。

完成人工验收后，我使用下列命令形式提交；尖括号内容是说明性占位符，执行前需替换：

```text
git add -- <已审阅文件路径>
git diff --cached --check
git diff --cached
git commit -m "<类型>(m1): <具体变更及目的>"
git push -u origin <当前任务分支>
```

首次推送并设置上游后，我使用 `git push` 同步后续提交。我会逐项暂存已审阅的文件，保留实际提交时间和验证记录，避免将其他成员的工作混入自己的提交。

以下是不同真实任务的提交信息示例，不是已经完成的工作，也不要求每 30 分钟刚好完成一项：

```text
docs(m1): clarify reservation acceptance cases
feat(m1): add seat availability query with validation
feat(m1): prevent overlapping reservations
test(m1): cover concurrent reservation conflicts
fix(m1): preserve repair restrictions after approval cancellation
```

### 8.3 自动化安排

目前尚未配置每半小时后台自动提交或推送的任务。我先在开发会话中执行上述检查流程；具体提交与推送结果以 Git 历史和 PR 记录为准。

官方文档说明，定时任务可用于周期性工作；访问本地项目时需要电脑开机、桌面应用运行，并且项目仍在磁盘上。具体可用性和配置应以实际应用为准，参见 [OpenAI 官方定时任务说明](https://learn.chatgpt.com/docs/automations?surface=app)。

如果后续启用自动化，我会先明确工作时段、停止条件、允许的任务分支和文件范围，以及验证要求。自动化负责准备差异与验证报告，或同步已经人工验收的提交；新改动仍由我按项目规则验收。

如后续确需无人值守自动创建提交，我会先与团队确认验收安排，再验证 GitHub 写权限与运行条件。本计划保留现有团队规则。

### 8.4 为课程保留的证据

我会保存完整的“需求 → Issue → 计划与确认 → Commit → 测试 → PR → 同行 Review”链路，在 PR 说明 AI 参与范围和人工检查结果。文档、测试、修复和接口实现均按实际成果记录。

我会提前与教师和团队确认评分依据，包括任务分支提交、合并后历史、PR 和个人贡献统计。若需要保留逐步提交历史，我会与仓库管理员确认合并策略，避免 squash 合并后在 main 上只看到一个汇总提交，并保留 PR 和任务分支记录。
